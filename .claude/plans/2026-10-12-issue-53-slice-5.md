| Implementer brief, dependencies | **Ids only**: `dependencies: task.depends_on.join(", ")` | `core/implementation-brief.ts:221` |

`docs/deterministic-core.md` §3 still says "the live gate and recorder stand down". For the recorder, that is now false.

The remaining `executing_tasks` inference happens in three places. All of them are legacy-only. They settle only through the untrusted legacy resolution, which stores the guessed Task's evidence but leaves it quarantined (`pending` and `revalidation_required`); none can complete one:

- **a.** `update-task-status.ts:323-352`: a transcript with no Task id, and exactly one Task executing.
- **b.** `update-task-status.ts:278-300`: an unreadable transcript, and exactly one Task executing.
- **c.** `pi/subagent-settlement.ts:270-291`: `resolveImplementationTaskId`. It extracts the Task id from the parent prompt, which is unproven for a batch, and then falls back to the sole executing Task (`inferred: true`).

Nothing forbids this inference structurally. Tests pin the current legacy behaviour.

## What remains, re-scoped

### Item 3 (the reason for the slice): predecessor output in the dependent brief

**The gap.** A dependent Task is dispatched only after its dependencies are `completed`:

- `depends_on` must name a Task in an earlier Wave (`state-file-wire.ts:919-925`).
- Dispatch refuses unless each dependency is `completed` (`validate-task-execution.ts:61-77`).
- A Task becomes `completed` only through a passing Wave Gate (`wave-gate-checks.ts:447-463`).

So the predecessor's facts are final and reviewed by dispatch time. The brief still shows only ids, and the implementer must rediscover what a predecessor produced by reading the plan, which is the drift window the issue names. The brief is already rendered by the engine, and its shell already loads the whole graph (`orchestration/implementation-brief.ts:37`). Only the pure renderer lacks the input.

**Design: a Predecessor Output section derived from protected state, with no model-authored content.**

```ts
// core/predecessor-output.ts (pure)
export type PredecessorOutput = Readonly<{
  taskId: string;
  description: string;
  completionClaims: readonly string[];   // its spec_anchors
  produced:
    | Readonly<{ kind: "recorded"; changed: readonly RepoPath[]; declaredUnchanged: readonly RepoPath[] }>
    | Readonly<{ kind: "unrecorded" }>;   // legacy completed Task with no files_modified
}>;

export function predecessorOutputs(task: Task, graph: TaskGraph):
  Either<PredecessorOutputError, readonly PredecessorOutput[]>;
```

- **Direct dependencies only**, in `depends_on` order. Transitive outputs are reachable through each predecessor's own claims, and listing them would inflate the brief.
- **Fail closed:** a dependency that is missing or not `completed` returns a typed error. The renderer refuses (`dependency-not-completed`) rather than rendering a brief that implies a finished predecessor. Dispatch already guarantees this, so the refusal backs up an invariant rather than handling a new case.
- **Parse, don't validate:** `files_modified` is currently checked only as "an array of strings" at the wire (`state-file-wire.ts:1001-1006`). Parse it into repo-relative `RepoPath` values at the boundary that builds `PredecessorOutput`, so absolute paths, `..` segments and empty strings cannot be rendered. A bad stored path is corrupt authority, so the renderer refuses rather than dropping it.
- **`unrecorded` is stated, not defaulted.** A legacy completed Task without `files_modified` renders "what it changed was not recorded; read its declared files", never as an empty list.
- **Rendering:** a new `{predecessor_outputs}` brief variable and a template section, "What your dependencies produced". It tells the implementer to read those files before writing code and not to re-implement what they export. With no dependencies it renders the literal `None — this Task has no dependencies.`
- `BRIEF_VARIABLES` and the template change together (the renderer refuses a mismatched template). `ImplementationBriefInput` gains `predecessors: readonly PredecessorOutput[]`, and the shell computes it from the graph it already holds.

**Not in this design: implementer-authored output.** A structured handback in which the implementer declares its exports and notes would be model-authored text. Nothing reviews it, and it would land in the next agent's prompt. That reopens the drift class this slice exists to close, and it conflicts with the arc plan's invariants #8 and #10. A later, separate option is an *engine-derived* export surface, parsing the predecessor's changed TypeScript files for exported names. That is language-specific, so I'd defer it until the path list proves insufficient.

### Item 1 (narrowed): per-caller phase gate on Claude Code

Replace `registry.soleActiveBinding(sessionId)` in `enforce-phase-tools.ts` with the same `attributeEvidence(parseCallerIdentity(input.agent_id), …)` decision the recorder uses:

| Attribution | Gate behaviour |
|---|---|
| `caller` | Gate against the caller's own binding. This is new: per-agent gating during parallel Waves |
| `sole` (no id reported, one active) | Gate as today |
| `contended` (no id reported, several active) | Stand down as today |
| `caller-unbound` | Pass through (the caller has no machine, e.g. the main agent) |
| `caller-ambiguous`, `caller-unparseable`, `corrupt` | Fail closed, matching the gate's existing "any binding exists → errors fail closed" policy |

One decision function then serves both the recorder and the gate, so they cannot disagree about who a tool call belongs to.

**Pi:** the `tool_call` guard cannot name its caller (`pi/extension.ts:300-303`), and Pi has no recorder, so Pi stays out of scope. Pi children are separate processes, so the remaining gap is the missing machine gate, not cross-crediting. I'll state this as a limit and not build it.

### Item 2: make "inferred" a type, not a convention

- Add one constructor, `inferSoleExecutingTask(graph): InferredTaskAttribution | null`, returning a branded `{kind: "inferred", taskId}`. The three legacy sites call it instead of reading `executing_tasks[0]` themselves.
- Pi's parent-prompt extraction (`subagent-settlement.ts:279`) is also classified as `inferred`, because a parent prompt in a batch names several Tasks.
- Every function that can mint a positive transition accepts only proven authority (`ImplementationAttemptAuthority`) and never an `InferredTaskAttribution`. The compiler enforces this, so no lint rule is needed.
- `applyUntrustedStopResolution` and the quarantine path take `InferredTaskAttribution | ProvenTaskId`.
- **Guard test:** add an architecture test (in the style of existing source-scan tests) that fails if `executing_tasks` is indexed (`[0]`) or length-tested to pick a Task outside `inferSoleExecutingTask`.

### Item 4: drop

Requirement Completion Claims are already enforced through the settled floor and the Requirement Coverage Projection (#41, #43, #78). This was the issue's own verdict.

## Decisions (delegated, 2026-10-12)

1. **Predecessor output is engine-derived only.** No implementer handback.
2. **Direct dependencies only.**
3. **The gate fails closed** on `caller-ambiguous`, `caller-unparseable` and `corrupt`.
4. **The Pi tool gate is stated as a limit**, not built.

## As implemented (differs from the design above)

- **Item 3:**
  - `core/predecessor-output.ts` holds `predecessorOutputs`, `renderPredecessorOutputs` and `predecessorOutputErrorMessage`.
  - The brief gets a `{predecessor_outputs}` variable and a "What Your Dependencies Produced" section. `ImplementationBriefInput` gains `roster`, and the shell passes `graph.tasks`.
  - A refusal is `predecessor-output-unavailable`.
- **Non-canonical `files_modified` is stated, not refused.** Legacy stop paths store raw transcript paths, so refusing would block dependents on older graphs. A third `produced` arm, `non-canonical`, reports how many entries were rejected and points to the declared files. It never renders the rejected text. A non-canonical *declared* path (`file_list`) is still refused, because the State File boundary already proves `file_list` canonical.
- **Item 1:** `phaseGateTarget` in `machine/evidence.ts` maps `EvidenceAttribution` to `gate`, `pass`, `stand-down` or `fail-closed`. `enforce-phase-tools` now uses it in place of `registry.soleActiveBinding`. The port method `SessionRegistry.soleActiveBinding` is kept: it is the tested projection of the sole-active invariant, used by about 40 assertions.
- **Item 2:**
  - `core/task-attribution.ts` adds `inferSoleExecutingTask`, which returns `{kind: "inferred", taskId}` or `{kind: "unattributable", executingCount}`. The two Claude legacy sites and Pi's `resolveImplementationTaskId` use it.
  - **No branded id.** A first cut branded the guess as `InferredTaskId`, but the brand widened to `string` at every consumer, so the compiler checked nothing (PR #79 review). The type that actually stops a guess is `ImplementationAttemptAuthority`: every positive settlement requires it, and a Task id cannot construct it.
  - Pi's binding replaces `inferred: boolean` with `attribution: "named" | "parent-prompt" | "sole-executing"` (`BoundImplementationTask`). Parent-prompt extraction is reclassified as a guess, and `unprovenAttribution` renders why.
  - A source-scan guard test (`tests/core/task-attribution.test.ts`) refuses any pick of a Task from the executing set outside the owner: indexing (`[0]`, `.at(0)`), destructuring, or a strict or loose length-1 test. It pins each form, and it pins membership and count reads as legal.
- No `@ts-expect-error` fixture was added, for the same reason: positive completion already requires `ImplementationAttemptAuthority`.
- **Docs:** the per-caller gating text landed in CONTEXT.md's **Guarded Skill Machine** entry, not in **Implementation Binding**: the gate is part of the machine, and the Binding governs writes and settlement.
- Line numbers cited in "The issue's premise" table describe main on 2026-10-12 and will drift; the symbol names are the durable reference.
