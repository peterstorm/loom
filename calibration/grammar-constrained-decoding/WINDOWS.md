A new window adds a table row and a paragraph. Nothing recorded here is edited or re-decided, and a window is never re-run to obtain a more favourable result.

The two blocked windows belong to **pilot-1** (`preregistration.json`, release policy `capable-route-required`). Two independent reasons block a done claim for them:

1. **The pilot could not run.** The live route `desktop-vllm` refused connections in both windows and on every manual check in between (`curl` exit 7). No sample was dispatched or invented. Every cell is retained as `not-measured`, with its preregistered pair count. The second window is not a re-run looking for a better result. It re-checks the route and records the delivered runtime identity, and it is blocked for the same reason as the first.
2. **Under pilot-1's policy the intended deployment has no qualified *capable* route.** In the spec glossary, a capable route accepts **and enforces** the declared constraints. The only qualified route, `(desktop-vllm, glm-5.3-flash-spark-tp2-v14, <digest>)`, is classified **unconstrained emission** (`probes/emission-qualification/`). AD-11 as first recorded says: *"If the intended deployment has no qualified capable route, the constrained feature cannot be declared measured/done."* The decision core encodes this as the missing measurement `no-qualified-capable-route`, so even a complete, all-passing pilot-1 window on this route stays `incomplete`. The retained pilot-1 windows keep that decision. They re-decide to exactly their retained bytes, and the re-decision tests pin this.

**The first pilot-2 window measured a route outage, not the arms.** Its first pairs ran normally (reviewer samples of 2.5–6 minutes, accepted payloads on both arms). Then the local vLLM stopped serving (the operator confirmed it had been down and was brought back up), and every remaining attempt on both arms ended within about 3 s after one model request with no answer. The runner of that revision had two defects that turned the outage into data:

1. **A provider error was recorded as a semantic rejection.** Pi ends a model turn whose request failed with `stopReason: "error"` and an `errorMessage`. The classifier read that transcript as "result carried no final text payload" (`extraction-failure`), so the outage was charged to the arm under test and spent the attempt-2 retry on a route that was down. **Fixed:** by the provider-error rule, stated once under [Measurement definitions](README.md#measurement-definitions) (`providerFailure`, `pilot-dispatch.ts`).
2. **Nothing stopped the window.** It walked the remaining ~400 pairs in minutes. **Fixed:** the route fail-fast (`pilot-window.ts`, below) stops a window when the route stops answering.

The window is retained exactly as recorded and keeps its window decision, `incomplete-missing-measurement`; it is evidence of the outage and of the two defects, and it measures nothing about emission. *As of 2026-10-08* the release was therefore still incomplete, and the next pilot-2 window was to run under the same preregistration: a re-check after an infrastructure failure, like pilot-1's second window — not a search for a better result, since the retained window records no model behaviour to improve on. That plan is history: two more windows ran on 2026-10-09 (below), and the operator release of ADR-0023 decision 5 then superseded the wait for a complete window. The window's own decision is unchanged.

**The second pilot-2 window** (`windows/gcd-ad11-pilot-2--2026-10-09T08-35-45-959Z/`) ran at revision `e8d688d8` from 2026-10-09 08:35:45Z and **ended aborted after 13 of 408 pairs** at 11:00:56Z (about 13:00 local time), when the route stopped answering. The fail-fast worked as designed: pair 12's extraction arm ended in a provider error (`EngineCore encountered an issue`) and the re-probe still found the route up, so the window went on; both arms of pair 13 then failed within about 3 s (`Connection error.`), the re-probe found `GET http://192.168.0.80:8000/v1/models` unreachable, and the window stopped with `route-unreachable` instead of spending the remaining 395 pairs on an outage. It is retained exactly as recorded, and its window decision is `incomplete-missing-measurement`: every cell is `not-measured`, because 13 pairs are far short of each cell's preregistered count. Its 26 samples are real measurements of both arms, but too few to judge any guardrail. **A caveat on its early samples:** during the window's first hours the same machine also ran review agents and full test suites, so local load may have lengthened Pi startup and tool latency for those samples; the window records no load figures, so this cannot be quantified or corrected after the fact. That revision applied the provider-error rule BEFORE classifying the transcript, so it also recorded an attempt whose payload had already been accepted (an emission-tool call the engine accepted, followed by a turn that ended in a provider error) as an `infrastructure-failure`. The current rule ([Measurement definitions](README.md#measurement-definitions)) classifies first and keeps such a payload. Such samples would be identifiable in that window's `observations.jsonl`: each would be an `infrastructure-failure` attempt with `toolAcknowledged: true` (and `emissionCalls` ≥ 1). The window holds none: all three of its infrastructure failures had no acknowledged emission call. The converse needs one check: an attempt of that shape whose acknowledged calls were ambiguous (two successful calls, a `duplicate-call` rejection) had no accepted payload, so it is an infrastructure failure under either rule. Its `window.json` is `schemaVersion` 1 and its fail-fast counted only all-infrastructure pairs (`consecutive-infrastructure-failures`), not timeouts; it stopped on the other reason, `route-unreachable`, which both versions share. Neither is rewritten: the window is evidence as recorded, and it is decided by its own record. *As of that morning* the next pilot-2 window was again planned as a re-check after an infrastructure failure, not a search for a better result; it ran the same afternoon (below), and the operator release of ADR-0023 decision 5 superseded any further one.

**The third pilot-2 window** (`windows/gcd-ad11-pilot-2--2026-10-09T14-43-58-835Z/`) ran at revision `fcafe6e7` (`window.json` `schemaVersion` 2) from 14:43:58Z and **ended aborted after 30 of 408 pairs** at 18:00:36Z, when `GET http://192.168.0.80:8000/v1/models` stopped connecting; the fail-fast stopped it with `route-unreachable`. Every cell is `not-measured` (reviewer v2 14/104, reviewer v3 4/104, judge 8/100, refutation 4/100 pairs: the 30 dispatched), so its window decision is `incomplete-missing-measurement`. Its descriptive figures, which are point values with no interval and no blinded assessment: the emission arm accepted 26 of 30 samples at attempt 1 with no semantic rejection; the extraction arm accepted 21 of 30 and ended 7 in `payload-refused` (`invalid-json`) after both attempts — 5 judge and 2 refutation samples whose final message the frozen verdict parser could not read as JSON (that parser is the emission tool's, so the retained detail reads "emission arguments are not valid JSON"; a later revision's detail names the final message). The window retains no refused text, so whether those messages wrapped valid JSON in a fence or prose cannot be told; the production refutation path unwraps an unambiguous fence or prose wrapper before parsing (`refutationVerdictJson`), while the pilot's frozen-parser ingestion, like the production judge path, reads the message as it is. Among accepted samples, emission's p50 / p95 dispatch-to-ingestion was 205 s / 310 s against extraction's 270 s / 543 s. One emission infrastructure failure (`reviewer-payload/v2#round15-vulnerable#r1`) had an acknowledged tool call but no accepted payload, so it is an infrastructure failure under the current rule. After this window the operator released the route by decision (the operator release, above) rather than wait for a window that completes.
