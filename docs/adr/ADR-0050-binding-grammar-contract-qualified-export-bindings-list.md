# ADR-0050: Binding grammar as a contract-qualified Export bindings list in File Structure

## Status
Accepted (2026-11-07). Shipped by G2 skeletons
(`.claude/specs/2026-11-02-g2-skeletons/spec.md`; plan `.claude/plans/2026-11-02-g2-skeletons.md`, AD-3,
interview Q5a). It refines ADR-0020 and does not supersede it. The engine skeletonizes only exports that a plan
binds to a contract's frozen types file, never internal helpers.

## Context
G2 has the engine write a deterministic TypeScript or Java skeleton at each bound implementation path. Each
skeleton is a set of stubs whose signatures come from a function-type alias that a contract's frozen,
compiled types file declares. The engine needs four facts before any of that can happen: which files are
bound, which exports each file provides, which alias types each export, and which contract owns that alias.
The specification already settled that these bindings live in the plan's `## File Structure`.

Several forces constrain the textual form:

- **Decided before the types exist.** FR-002 and AS-002..AS-005 require plan validation to refuse a bad
  binding before population. A file that references two contracts (AS-004) has to be refused at that point,
  and no types file exists yet. So the contract qualification has to be written in the plan text. It cannot
  be inferred later from which types file happens to declare the alias.
- **Generated bytes splice plan text.** Export names and aliases end up inside engine-written source. If an
  identifier is unchecked, the plan becomes a code-injection channel (Q11a). Identifiers must be validated so
  that the generator splices nothing else into the source.
- **Existing grammar and stray detection.** `parse-plan-models.ts` already reads column-0 `**Label:**`
  lists (the `labelledList` grammar) and reports labels found in the wrong section as `misplaced-label`
  strays. File Structure's fenced blocks are free-form trees that the engine does not parse.
- **Decompose copies, it does not author.** `phase-decompose.md` has to carry the bindings into the
  TaskGraph verbatim. The form has to be line-oriented and stable under copying.
- **Graph-shape consistency.** A binding is only meaningful when some non-contract Task implements the
  path, and that Task runs after the contract Task. The contract Task never lists the path itself, because
  the engine writes the stubs there (AD-9). No waiver may declare the path to be non-production.

## Options Considered

1. **A column-0 `**Export bindings:**` labelled list under a group's fenced block in File Structure, one
   contract per line (chosen)**
   - Pros: reuses the proven `labelledList` regex grammar and its `misplaced-label` stray detection, so no
     new parser family is needed. It sits where the specification put bindings ("bound via File
     Structure"). Each line names its contract, so AS-004 can be decided from the text alone. A one-line,
     one-file form round-trips exactly (`renderExportBinding` and back), which makes the TaskGraph stamp and
     `bindingStampAgreement` drift detection trivial. Decompose copies it verbatim.
   - Cons: the binding sits next to the file tree instead of inside it, so a path is written twice (once in
     the tree, once in the list). All exports of a file must fit on one line, which can get long.

2. **A fenced trailer, where bindings are annotated on the fenced File Structure tree lines**
   - Pros: each path appears once, next to its tree entry.
   - Cons: the engine would have to start parsing fenced File Structure lines, which today are free-form
     prose trees with no grammar. A new, fragile parser would have to tell annotation from description text.
     It has no existing stray detection.

3. **A binding list inside each `### CT-N` contract block**
   - Pros: groups bindings with the contract they bind to, and the contract qualification is implicit.
   - Cons: contradicts the specify-phase decision that bindings live in File Structure. It splits a
     file's description from its binding. AS-004 becomes a cross-section duplicate check instead of a
     per-line fact. Contract blocks start to carry implementation-file concerns.

## Decision
**Bindings are declared in `## File Structure` as a column-0 `**Export bindings:**` list, outside any
fence and directly under a group's fenced block. Each `- ` item binds one file to exactly one contract.**

```
**Export bindings:**
- `src/order/pricing.ts` — CT-1: priceOrder: PriceOrderFn, parseOrder: ParseOrderFn
- `src/main/java/com/acme/order/Pricing.java` — CT-2: priceOrder: PriceOrderFn
```

**Grammar** (`engine/src/core/skeleton/bindings.ts`):

- **Parsing.** `parseExportBindings` is pure and total. It reads every `**Export bindings:**` label in the
  File Structure section through the `labelledList` grammar. Blank lines may come before the first item, and
  the list ends at the first line that is not an item. It returns an `ExportBindingsDeclaration
  { bindings, problems }`. A problem is collected as a `BindingProblem`, never thrown.
- **One contract per line.** If a path appears on lines that name different contracts, the result is
  `multi-contract` (AS-004). If it appears on two lines of the same contract, the result is
  `duplicate-path`. A path with any path problem contributes no binding.
- **Identifiers.** Every name and alias is minted by `parseIdentifier`, the only `Identifier` constructor.
  It must match `^[A-Za-z_][A-Za-z0-9_]*$` and must not be in the single fixed reserved-word list that
  covers TypeScript and Java. Generated skeleton bytes therefore contain only validated identifiers and fixed
  template text.
- **Malformed entries.** Each malformed entry is a `malformed-entry` problem with a closed reason:
  `not-a-binding-line`, `missing-contract`, `missing-name`, `missing-alias`, `empty-exports`,
  `invalid-identifier` or `reserved-word`. A repeated export name in one file is `duplicate-name`.
- **Misplacement.** `parse-plan-models.ts` calls `parseExportBindings` on the File Structure section. A
  label found in any other section is a `misplaced-label` stray, never an opt-out.
- **Canonical form.** `renderExportBinding` emits the canonical line, and parsing that line yields the same
  binding.

**Validation** (`validateExportBindings`, run inside `validateModelBindings` in
`engine/src/handlers/helpers/validate-model-bindings.ts`, and re-run by
`engine/src/core/task-graph-population.ts` before stamping). Each refusal is rendered by
`renderBindingProblem` and names the file and the reason (FR-002):

| Problem kind | Refused when |
|---|---|
| `unsafe-path` | the path fails `isRepoRelativePlanPath` |
| `frozen-path` | the path is a frozen types file or acceptance test of some contract |
| `unknown-contract` | the CT id is not declared by the plan |
| `contract-without-types` | the contract declares `**Types file:** none` (nothing to bind to) |
| `bound-on-contract-task` | the path is in the contract Task's own `file_list`, which the engine writes (AD-9) |
| `unheld-path` | no non-contract Task lists the path |
| `holder-not-after-contract` | a holder Task does not depend, directly or transitively, on the contract Task |
| `bound-on-waived-task` | a holder's regression waiver is `documentation-only` or `generated-artifact` (Q15a) |

A malformed contract is reported by contract validation, not again here. A bound path in a language other
than TypeScript or Java is accepted. At its spawn it reports "unsupported language, no skeleton" (AS-040).

**Persistence handoff.** Population stamps the validated bindings into the TaskGraph as `export_bindings`
in plan order (AD-4). `bindingStampAgreement(plan, stamp)` compares the rendered lines, and the brief shell
refuses a spawn on drift until re-population. `references/plan-template.md` and
`commands/templates/phase-decompose.md` document the label and tell decompose to copy it verbatim.

## Consequences

**Positive:**
- AS-004 and every other FR-002 refusal is decided from plan text alone, before population and before any
  types file exists.
- No new parser family: the label rides the existing `labelledList` grammar and `misplaced-label` stray
  detection, and the fenced File Structure trees stay unparsed.
- Identifier validation at the grammar boundary means generated skeleton and contract-stub bytes cannot
  carry injected code. No new trust boundary was needed (Q11a).
- The canonical one-line form makes the TaskGraph stamp exact and drift detection a plain line
  comparison.
- The `BindingProblem` union is closed, and rendering matches over it exhaustively, so a new refusal kind
  cannot ship without an operator message.

**Negative:**
- Every bound path is written twice in File Structure, once in the fenced tree and once in the list. The
  engine never cross-checks the two, so a tree entry and its binding can disagree in spelling. Only the
  binding and the Task `file_list` checks are authoritative.
- A file that provides exports from two contracts cannot be bound at all. It must be split or bound to a
  single contract, which is a deliberate restriction on plan shape.
- One file's exports must all fit on one line, so long export lists give long lines that are awkward to
  edit or review.
- The reserved-word list is fixed and covers both languages, so a name that is legal in one language but
  reserved in the other (for example a Java keyword used as a TypeScript export) is refused in both.
- Bindings on an unsupported language are accepted silently at validation. The operator only learns at
  spawn time that no skeleton will be written.
