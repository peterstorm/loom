# ADR-0004: Engine-Owned Orchestration Automation

## Status
Accepted

## Context

Loom's orchestration mechanics lived in prose. The wave gate, the architecture
and refutation panels, standalone review, status reporting, and remediation
staging were each described as a sequence of `jq` queries, shell pipelines, and
helper invocations that an LLM orchestrator was expected to execute in order.

That arrangement has three failure modes, and all three were observed rather
than hypothesised. A parent model can skip a step, and nothing notices — the
step exists only as an instruction. A parent model can derive a decision from
raw state fields that the engine would have judged differently, so the
operator's view and the gate's view disagree with no way to tell which is
right. And a procedure written twice — once for Claude Code, once for Pi —
drifts, because nothing forces the two transcriptions to stay equal.

The mechanics themselves are deterministic. Which reviewer slots are
outstanding, whether a roster is complete, whether a staged path set matches
an audited one, what the next action is — none of these require judgement.
Only two things genuinely do: the semantic work an Agent performs, and a real
user decision. Everything between them is computation that was being asked of
a language model.

## Options Considered

Three candidates were generated by an architecture panel (run
`run.RIzvYedN0m`, manifest at
`.claude/specs/2026-08-09-orchestration-automation/panel-runs/run.RIzvYedN0m/manifest.json`),
each written through a distinct lens, then scored adversarially by three
judges against criteria derived from the interview.

1. **`candidate-simplicity-first.md`** — one façade, one session object, direct
   reuse of the existing reducers and helpers.
   - Pros: lowest effort; best brownfield fit; one parent-facing contract;
     strong pure core retained
   - Cons: publication, persistence, dispatch, and Fugue adaptation remain
     insufficiently explicit in its replayable core

2. **`candidate-type-driven-fp.md`** — closed domain programs with pure
   reducers, parser-produced authority proofs, immutable effect
   intents/receipts, persistent execution.
   - Pros: strongest pure functional core; illegal states unrepresentable;
     roster completeness provable rather than assumed
   - Cons: substantially more type and module surface; original scope was too
     broad for the codebase it extends

3. **`candidate-risk-security-first.md`** — hash-linked evidence, mandatory DAG
   execution for every query, write-ahead machinery.
   - Pros: strongest hardening; narrowest authority boundaries
   - Cons: mandatory DAG execution per query and write-ahead machinery conflict
     with the stated simplicity axis

**Computed ranking (authoritative, from `ranking.json`):**

| Rank | Candidate | Total | simplicity / pure core / fit + effort |
|---:|---|---:|---|
| 1 | `candidate-simplicity-first.md` | 25 | 8 / 8 / 9 |
| 2 | `candidate-type-driven-fp.md` | 20 | 4 / 10 / 6 |
| 3 | `candidate-risk-security-first.md` | 16 | 2 / 9 / 5 |

The panel recommended rank 1. **The user selected rank 2.** That divergence is
recorded deliberately: the panel optimised for the stated simplicity axis,
while the user weighted the 10/10 pure-functional-core result and asked for
substantially more use of Fugue. A panel ranking is advice, not authority.

## Decision

**Adopt `candidate-type-driven-fp.md` as the base, grafting the winner's
minimal contract and the risk candidate's narrow authority boundaries to
control its cost.**

### Grafts

- From simplicity-first: ONE parent-facing façade and ONE minimal external
  action contract — `spawn-batch`, `await-user`, `blocked`, `done`. Existing
  reducers, stores, `StateManager`, and helpers are reused rather than replaced
  by a workflow registry.
- From type-driven-fp: only a parser produces `CompleteRoster<AcceptedResult>`,
  and aggregation APIs accept nothing else. A partial roster cannot reach a
  ranking or a tally.
- From risk-security-first: an anchored `RunDirHandle` exposes fixed artifact
  operations with no arbitrary path API; validation and routing nodes are
  capability-free; narrow adapters own filesystem, protected-state, harness,
  and Git effects.

### Authority model

Request authority — not caller prose — selects run, slot, attempt, model,
skill, context, and destination. Every spawn binds an engine-issued
`AgentRequestAuthority`; no request is executable before its artifact batch is
durable; and a captured result is bound to the request it claims to answer,
because an accepted transcript becomes the evidence a roster proof is built
from. A result admitted under the wrong identity would be indistinguishable
from the genuine one it displaced.

### Fugue used directly; no AuthoredDag sidecar

Fugue 0.4.0 is used through its **main public export only** — `Machine`,
`JobLike`, `runStateMachine`, `replayEvents`, `toJson`/`fromJson`,
`defineDag`, `runDag`, `createTransformNode`, `createHumanReviewNode`,
`defineFanOut`, `runResumableDagJob`. No private or `/advanced` import, and no
Redis or BullMQ: durability is a local run directory.

A plan-level `AuthoredDag` sidecar was explicitly **rejected**. Local
`AuthoredDag` v1 permits one DAG in one of five single shapes, requires each
node to occupy exactly one structural role, and Loom permits one sidecar per
plan. This feature needs several distinct operation DAGs plus persistent
event-driven machines and roster-sized batches represented as values. Forcing
them into one sidecar would have required either a generic DSL or primitives
Fugue 0.4.0 does not have. The executable sources are the imported lifecycle
machines and the direct Fugue calls — no decorative graph artifact was
created.

### Known boundary

Fugue 0.4.0 has no Agent node, nested subgraph, cross-node loop, or dynamic
fan-out. Semantic work is therefore a returned `spawn-batch` rather than a
node; retry is machine state across resumes rather than a back-edge; and
roster-sized work stays a `NonEmpty`/`ExactRoster` value inside static nodes.
Adding any of those requires a Fugue release and a new decision.

## What shipped

Eleven implementation slices across `engine/src/core/` and a new
`engine/src/orchestration/` layer, plus harness capture:

| Slice | Landed as |
|---|---|
| Authority kernel, panel programs, lifecycle machines | `core/orchestration-contract/`, `core/panel-program.ts`, `core/wave-gate-machine.ts`, `core/standalone-review-machine.ts`, `core/remediation-machine.ts` |
| Fugue runtime | `orchestration/fugue-program-runtime.ts` |
| Anchored run directory, context packets, effect receipts | `orchestration/run-directory-handle.ts`, `context-packets.ts`, `effect-runner.ts`, `no-follow-fs.ts` |
| Four static operation DAG families + capability registry | `orchestration/dags/*-operations.ts`, `orchestration/dags/capabilities.ts` |
| Remediation Git boundary | `orchestration/git-remediation.ts` |
| Façade and status | `handlers/helpers/orchestration.ts` |
| Cross-harness capture | `core/harness-capture.ts`, `handlers/subagent-stop/capture-orchestration-result.ts` |
| Pi façade-to-harness handoff | `orchestration/session-run-bindings.ts`; façade spawn actions publish session-scoped run/request authority that Pi binds to native tool-call identities before dispatch |

Five findings from implementation are recorded because each contradicted an
assumption in the plan and would otherwise be rediscovered:

- **Fugue conditional/default edges make their source OPTIONAL**, which
  switches the downstream node's input from the bare upstream value to an
  object keyed by source node id. Branch nodes model that envelope explicitly.
- **A Fugue DAG's output node must be reachable along unconditional and
  default edges**, so each graph converges on one terminal decision rather than
  an output that exists only when a predicate matched.
- **Fugue ids reject `.`**, which every Loom run id carries. The lowering maps
  `.` to `:` and refuses a source id already containing `:`, keeping it
  injective.
- **`--literal-pathspecs` is a GLOBAL Git option**; a subcommand given it as
  its own flag exits 129. It is prepended in one seam so no operation can
  misplace or omit it.
- **Git treats a MISSING `GIT_INDEX_FILE` as an EMPTY index**, so reading a
  discarded temporary index reported every tracked file as deleted — a
  plausible staged set describing a change nobody made.

The benchmark measures the status path the façade replaced: 8 parent `jq`
invocations (890 characters) become 1 (56) — 87.5% fewer calls and 93.7% fewer
characters, against mandated floors of 70% and 80%.

## Consequences

**Positive:**

- Deterministic mechanics are executed by code, so a step cannot be skipped by
  a parent that did not read its instruction.
- Status derives ONE `LoomStatus` value rendered two ways, so the human and
  machine forms cannot disagree with each other or with the program that
  decides readiness. Unparseable authority yields every category as
  `unavailable` and a `blocked` action rather than fabricated zero-or-ready
  values.
- Pi and Claude Code share the capture rules, so byte equality across harnesses
  is a property rather than a coincidence.
- Effects are idempotent across resumes: an effect whose id already recorded a
  receipt is reconciled rather than re-run.
- Failure is closed at every boundary added — publication, staging, capture,
  and installation each leave the world unchanged on refusal.

**Negative:**

- Substantially more type and module surface than the ranked-first candidate.
  This was the panel's central criticism (simplicity 4/10) and it stands.
- A second execution substrate (Fugue) is now a hard dependency, pinned at
  exactly 0.4.0. Its conditional-edge and id constraints shape Loom's graphs.
- Migration retains read-only compatibility by design: historical helpers/formats
  remain behind `core/legacy-archive.ts` and historical runs are never rewritten.
  Pi's spawn path now receives run
  authority through a session-scoped façade handoff rather than impossible
  child-to-parent environment mutation, but the plan's full five-scenario
  lifecycle benchmark is still broader than the reported status benchmark.
- The two orchestration layers must not import each other. This is enforced by
  a boundary rule that, until it was repaired during this work, had never
  actually run.
