# ADR-0055: Canonical skeleton bytes are deterministic and unformatted

## Status
Accepted (2026-11-07). Shipped by the G2 skeletons run (plan `.claude/plans/2026-11-02-g2-skeletons.md`, AD-8;
interview Q8a, Q16c). Builds on ADR-0042 (the TypeScript compiler API enters only through pure seams).

## Context
G2 has the engine write a skeleton file for each export binding when a Task spawns. Each file is a compiling
placeholder that implements a frozen contract alias and throws `unimplemented`. Contract stubs are also written
when the contract Task stops. The spec makes two promises about these bytes. Generation is deterministic: the
same frozen types and bindings produce byte-identical output (FR-009). Generation is idempotent: re-running over
an untouched skeleton changes 0 bytes (FR-010). The engine records each skeleton's SHA-256 (FR-031). It uses
that digest to tell an untouched skeleton from one a human or Agent edited. The no-clobber writer, the
declared-artifact digest subtraction at settlement, and the Contract Revision refresh with its `stale` flag
(FR-033) all depend on that comparison. If the bytes vary at all between runs, machines or environments, an
untouched skeleton looks modified. The writer then refuses to refresh it, and settlement credits engine bytes
to the Agent.

Two facts about the bytes do not follow from the types file alone. First, a TypeScript skeleton has to import
its alias from the types file, and the right relative specifier style depends on the project's module
resolution. The style may be extensionless, `.js` or `.ts`, and the wrong one does not compile. Second, the
layout: projects run prettier, google-java-format or nothing, each with its own configuration, and the
skeleton must still be a valid input to the project's compiler and linter.

The generator also has to stay in the functional core. It runs inside the spawn reservation and the stop
shells, and the conformance judge, the status report and the brief all reason about what it produced.

## Options Considered

1. **Pure generator, canonical unformatted layout, specifier style copied from the frozen acceptance tests (chosen)**
   - Pros: bytes are a pure function of target, frozen surface, contract, resolved bindings and one observed
     specifier style, so FR-009 and FR-010 hold by construction. The specifier style comes from files that are
     already frozen and compiler-checked at the contract Task's Wave Gate, so it is proven to resolve. No new
     shell I/O beyond reading acceptance files the engine already reads. No dependency on any tool installed in
     the environment.
   - Cons: the skeleton may not match the project's formatter, so a formatter or lint run can flag the first
     diff. The first-importing-file rule is a heuristic: a project that mixes specifier styles gets whichever
     style the first such file uses.

2. **Read `tsconfig` `moduleResolution` (and `allowImportingTsExtensions`) to pick the specifier style**
   - Pros: follows the configuration the compiler actually uses.
   - Cons: shell I/O and `extends` chain resolution for a fact the frozen acceptance files already prove.
     Monorepos with several tsconfigs make "which config" its own question. The mapping from resolution mode
     to style is a second model of the compiler that can drift from it.

3. **Run the project formatter (prettier, google-java-format) over generated bytes**
   - Pros: the skeleton matches house style from the first byte.
   - Cons: the bytes would depend on the environment: formatter presence, version and configuration. That
     breaks FR-009 across machines and breaks FR-010 whenever the formatter is upgraded. It needs process
     spawning inside the spawn reservation, which adds latency and a new failure mode. The generator could no
     longer be pure.

4. **Derive a full parameter list per function alias (TypeScript) instead of a zero-parameter arrow**
   - Pros: the skeleton reads closer to the final implementation.
   - Cons: deriving parameter names and types needs type-aware reading or text-copied signatures, so the output
     depends on more of the types file. Unused parameters trip `noUnusedParameters`. A zero-parameter throwing
     arrow is already assignable to any non-generic function type.

## Decision
**`engine/src/core/skeleton/generate.ts` produces each skeleton's bytes as a pure, total function in one fixed
unformatted layout. The TypeScript import specifier style is copied from the frozen acceptance tests. No
project formatter ever runs.**

- **Entry point.** `generateSkeleton: GenerateSkeletonFn` (types in `engine/src/core/skeleton/types.ts`)
  takes a language-correlated `TsSkeletonInput | JavaSkeletonInput`. Each input carries a `SkeletonTarget`
  (AD-15), the frozen surface, the contract id and the resolved exports. It returns
  `{ path, language, bytes, sha256 }`, the digest computed with `sha256Hex` over the exact bytes. An
  unsupported path cannot be built into a `SkeletonTarget` (`skeletonLanguageOf` in `language.ts` refuses it
  first), so the generator has no language refusal that could drift from the AS-040 "unsupported language, no
  skeleton" outcome. Generation is total.
- **Common layout.** LF line endings, exactly one trailing newline, no timestamps. One header comment:
  `// Skeleton written by Loom from <typesPath> (<contract>). Make these signatures work; keep each name and its type.`
  Exports appear in plan binding order. Imports are unique and sorted in code-unit order, never by locale. The
  file holds exactly the bound exports and the imports they need (FR-008).
- **TypeScript.** One `import type { <aliases> } from "<specifier>";`, then for each export
  `export const <name>: <Alias> = () => { throw new Error("unimplemented: <name>"); };` on three lines (the
  declaration, the throw and the closing `};`), preceded by a blank separator line. Generic
  aliases are refused earlier, at stage-two resolution (`resolve.ts`, AS-009). The specifier is relative to
  the skeleton's directory. Its style (`SpecifierStyle = "extensionless" | ".js" | ".ts"`) is the one used by
  the first frozen TypeScript acceptance file, in declaration order, that imports the types file. That file is
  found by `observeSpecifierStyle` in `engine/src/orchestration/frozen-surface-observation.ts`, which reads
  through the `typesImportSpecifier` seam in `ts-surface.ts`. If no acceptance file imports the types file,
  the style is extensionless. A `.js` style maps `.tsx`/`.ts` to `.js`, `.mts` to `.mjs` and `.cts` to `.cjs`.
- **Java (AD-7).** A `package` line from the target's path under `src/main/java/`, then
  `import <package>.<Holder>.<Alias>;` for each alias. Next comes `public final class <FileBasename>` with a
  private constructor and, for each export, a `public static final <Alias> <name>` lambda whose arity is the
  single abstract method's. Its body throws `UnsupportedOperationException("unimplemented: <name>")`. A holder in
  the default package cannot be imported (JLS 7.5), so there each member is typed `<Holder>.<Alias>` instead.
- **Invariant.** The only shell input to the bytes is the observed specifier style. Everything else comes from
  the frozen types file and the stamped bindings. Regenerating from the same inputs reproduces the recorded
  `sha256`. The writer (`engine/src/orchestration/skeleton-writer.ts`) and the Contract Revision refresh
  (`engine/src/core/contract-revision.ts`) rely on that equality to treat a file as untouched.

## Consequences

**Positive:**
- FR-009 and FR-010 hold by construction, and tests check them directly against `generate.ts` without fixtures
  for formatters or tsconfigs.
- The engine-written digest is stable across machines and tool upgrades. No-clobber refreshes, settlement
  digest subtraction and `stale` flagging therefore never misread an untouched skeleton as edited.
- The import specifier is one the project's compiler has already accepted in the frozen acceptance tests, so
  the skeleton compiles under the project's real module resolution without the engine modelling it.
- No new dependency and no process spawning inside the spawn reservation, so the generator stays in the pure
  core with the other skeleton derivations.

**Negative:**
- Skeletons can differ from house formatting, for example quote style, indentation width or import grouping. A
  project formatter or format-check lint may report the engine-written file until the implementing Agent
  reformats it. The Agent's edits replace the skeleton anyway.
- The specifier rule trusts the first importing acceptance file. A contract whose acceptance files mix styles,
  or import the types file only through a barrel, gets the first file's style, or extensionless when none
  imports it directly. Extensionless can fail under `node16`/`nodenext` resolution.
- The zero-parameter arrow says nothing about parameter names, so the Agent reads the types file for them.
  Generic function aliases cannot be skeletoned and are refused at resolution, not adapted.
- Any future change to the canonical layout changes every digest. Skeletons written before that change would
  read as modified, so a layout change has to be treated as a migration, not a cosmetic edit.
