# Claude Code and Pi integration guide

Loom supports Claude Code and Pi from one repository. This document explains the mapping for maintainers migrating or adding shared behavior. For installation and day-to-day Pi use, read [Using Loom with Pi](pi-usage.md).

## Design goal

Harness adapters should differ only where the harnesses differ. Domain policy, persisted types, parsers, reducers, model profiles, lint, proof, panel logic, and orchestration programs remain shared.

```text
Claude Code hooks ─┐
                   ├─ handlers/parsers ─ deterministic core ─ persistence/effects
Pi extension ──────┘
```

A feature is not migrated when two prose implementations merely look alike. Shared behavior must call the same core function or be pinned by parity tests.

## Concept mapping

| Claude Code | Pi | Shared Loom seam |
|---|---|---|
| Plugin manifest | Pi package `package.json` | Package root derived by each adapter |
| Slash command markdown | Rendered prompt/Skill resources | Shared `commands/`/`skills/` source |
| Agent markdown | Generated user Agent definition | `core/model-profiles.ts`, `utils/render-pi-agent.ts` |
| PreToolUse | `tool_call` | Core guards/validators |
| PostToolUse | `tool_result` | Linter/evidence/capture adapters |
| SubagentStart/Stop | subagent tool call/result lifecycle | State transitions and capture core |
| SessionStart | extension session hooks | cleanup/resume helpers |
| `${CLAUDE_PLUGIN_ROOT}` | rendered absolute package root | `pi/resources.ts` |
| in-process child | separate Pi process | Pi write grants and native correlators |
| `AskUserQuestion` in child | unavailable in headless child | unresolved relay; fail-fast where required |
| `.claude/state/` | `.pi/state/` | `StateManager`, harness-aware config |
| `.claude/linter/` | `.pi/linter/` | same loader and rule types |

## Package layout

The root package is both Claude plugin source and a Pi package:

```text
.claude-plugin/plugin.json    Claude metadata
hooks/hooks.json              Claude lifecycle registration
hooks/scripts/                thin Bun CLI shims
package.json                  Pi extension registration
pi/extension.ts               supported Pi adapter
pi/resources.ts               content-addressed resource renderer
pi/transcript-adapter.ts      Pi message/result lowering
pi/write-grant.ts             Pi child capability lifecycle
engine/src/                   shared engine
commands/ skills/ agents/     shared semantic resources
```

`package.json` statically registers only `pi/extension.ts`. Commands and Skills are contributed dynamically at `resources_discover` after rendering. This prevents Pi from loading unexpanded Claude tokens.

## Package identity

Claude Code expands `${CLAUDE_PLUGIN_ROOT}` in plugin resources.

Pi has no equivalent token. `pi/extension.ts` derives the active package root from its own `import.meta.url`, then `pi/resources.ts` lowers every shared root token to that exact path. The extension exports `LOOM_PLUGIN_ROOT` to children for diagnostics.

Never infer package identity from:

- current working directory;
- a Git root;
- a Claude plugin cache while running Pi;
- another installed copy of Loom.

Roots with characters that cannot be safely interpolated into all historical shared shell snippets are rejected rather than partially escaped.

## Resource rendering

Pi materializes commands, Skills, references, and rules into a content-addressed cache below `${PI_CODING_AGENT_DIR:-$HOME/.pi/agent}`.

The renderer:

1. inventories the complete source trees;
2. rejects symbolic links;
3. replaces package-root tokens;
4. hashes rendered bytes and inventory;
5. publishes atomically;
6. verifies every file on reuse;
7. quarantines/rebuilds corrupted cache entries.

A new resource category must be added to both renderer inventory and parity tests. Do not solve it with a cwd-relative path in one command.

## Agent definitions and model policy

Claude source Agents carry `model-profile`, Claude `model`, tools, and declared Skills.

Pi Agent definitions are generated by:

```bash
bash scripts/sync-pi-agents.sh
```

Generation:

- resolves the semantic profile;
- emits exact Pi provider/model/thinking frontmatter;
- lowers package paths;
- inlines declared Skill content, including command-backed phase Skills;
- stamps Agent and full-definition integrity metadata.

Before every Pi spawn, Loom freshly renders the active source and byte-compares it with the generated user Agent. It rejects stale bytes, project-local shadow definitions, unresolved tokens, and missing required-Skill context.

Pi launcher routing may explicitly inherit a local parent model. That is launcher policy at the spawn boundary, not an implicit fallback in Loom’s profile catalog.

## Tool-call guards

Shared pure/core functions decide:

- phase order;
- Wave/dependency/review order;
- unresolved prompt-template variables;
- expected model and Skill;
- direct-edit policy;
- state-path Bash policy.

Claude handlers adapt hook JSON to those inputs. Pi `tool_call` handlers adapt Pi input. Both must use the same protected-state read seam so “no active orchestration” and malformed-state behavior cannot drift.

A migrated guard needs:

1. a harness-neutral input/result function;
2. Claude adapter wiring;
3. Pi adapter wiring;
4. fail-closed top-level behavior where the call is enforcing;
5. parity tests with equivalent payloads and malformed authority.

## Subagent identity and writes

Claude subagents run inside the harness lifecycle and can be recognized by active-subagent tracking. Pi subagents are separate processes, so parent PID/flag assumptions do not transfer.

### Pi write grants

The parent issues one one-time capability per spawn item. A grant is bound to:

- Agent;
- repository cwd;
- parent session;
- Task id for implementation work, or derived artifact directories for writer roles;
- expiry and one-time token digest.

Implementation Agents receive whole-session Task-bound write authority. Phase/panel writer Agents receive only prompt-derived artifact scope. Read-only roles—reviewers, judges, verifiers, decompose, spec-check—receive no grant even if their prompt mentions paths.

The child consumes the token before its first model turn and creates a session-local binding. Replay, mismatch, expiry, failed spawn, or shutdown fails closed. Parent completion/rejection revokes unused grants.

When adding a new writer role, update the role-driven artifact-scope policy and its tests. Never infer permission from “the prompt contains a path.”

## Completion and transcript adaptation

Claude SubagentStop has transcript-path conventions. Pi produces structured messages and tool results. `pi/transcript-adapter.ts` lowers Pi messages into the evidence/review representations expected by the shared parsers.

For registered orchestration programs, both harnesses follow the same stronger path:

1. the engine reserves `AgentRequestAuthority` and a fixed transcript slot;
2. the adapter records harness-native id → request correlation at spawn;
3. on completion, the adapter selects the exact final payload under harness-specific rules;
4. `harness-capture-runtime.ts` publishes exact bytes into the reserved slot;
5. the program resumes and parses semantics from that immutable capture.

The parent model never copies output. Missing, duplicate, mismatched, surplus, or malformed capture fails closed.

## Phase advancement and proof

Both adapters reuse phase transition resolution, artifact parsing, task-id extraction, modified-path reconciliation, test-evidence interpretation, Finding parsing, and spec-check parsing.

Pi structured test evidence is not relabeled as Claude ledger trust. Provenance is part of the persisted result. Likewise, a Pi Agent’s artifact change is checked against its baseline and grant scope before proof is updated.

## Interactive phase limitation

Pi’s normal subagent extension launches print/JSON children with no UI. `ctx.ui` dialogs cannot reach the parent session. Therefore templates that require a live questionnaire are not fully equivalent to Claude Code.

The architecture-panel interviewer is explicitly refused in `pi/extension.ts`; accepting a digest without a real interview would corrupt lens and criterion authority. Standard interactive phase Agents remain subject to the same transport limitation even where no dedicated fail-fast role check exists.

The proposed solution is a parent-driven RPC child with dialog relay, documented in [Pi phase-agent interviews](pi-phase-agent-interviews.md). Until implemented, use Pi for non-interactive workflows or ensure required decisions are already explicit and do not claim questionnaire parity.

## State and linter paths

Harness selection chooses:

| Concern | Claude | Pi |
|---|---|---|
| TaskGraph | `.claude/state/active_task_graph.json` | `.pi/state/active_task_graph.json` |
| Project regex rules | `.claude/linter/rules/` | `.pi/linter/rules/` |
| Programmatic config | `.claude/linter/config.json` | `.pi/linter/config.json` |

The same `StateManager`, rule loader, linter core, and programmatic rules are reused. `PI_CODING_AGENT` or explicit `PI_CODING_AGENT_DIR` identifies Pi operation.

## Adding shared functionality

Use this checklist:

1. **Place policy in the core.** No harness imports, filesystem, env, clock, or process access unless the module is explicitly shell code.
2. **Parse untrusted boundaries.** Do not cast hook/Pi JSON or persisted data.
3. **Define adapter inputs.** Keep harness-specific extraction small.
4. **Wire Claude and Pi.** Preserve each harness’s blocking/error polarity.
5. **Handle identity.** If subagents/results are involved, use request authority and native correlators.
6. **Handle writes.** Decide whether the role needs Task-bound, scoped, or no write grant.
7. **Render resources.** Include any new shared files in Pi materialization.
8. **Test parity and faults.** Include stale/malformed/missing/symlink/duplicate cases.
9. **Document the real limitation.** Do not describe unsupported UI or transport as available.

## Validation

```bash
bash scripts/sync-pi-agents.sh
cd engine
bun run typecheck
bun run test:unit
bun run test:smoke
```

Focused Pi suites include:

```bash
bunx vitest run tests/pi-imports.test.ts
bunx vitest run tests/pi-resources.test.ts
bunx vitest run tests/pi-extension-review-events.test.ts
bunx vitest run tests/pi-write-grant.test.ts
bunx vitest run tests/runtime-resource-portability.test.ts
```

Run `/reload` and exercise the changed command from a project with the intended package scope.

## Legacy bridge

The legacy `pi/loom-bridge.ts` bridge was removed entirely: its historical partial roster could lose review/spec evidence, which is why it never received new behavior. `pi/extension.ts` is the only supported adapter, and the Pi package manifest pins the bridge's absence.
