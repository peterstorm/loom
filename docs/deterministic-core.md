# Loom’s deterministic core

Loom uses models for judgment and code for authority. A model may design, implement, review, or argue that a Finding is wrong. It may not decide whether an exact roster is complete, whether evidence belongs to a request, whether a Wave may advance, or which files enter a commit.

This document explains the guarantees that replace prompt-only coordination.

## The problem with prose-only orchestration

Prompt workflows drift in predictable ways:

- a plan describes one lifecycle while implementation creates two transition tables;
- an Agent says “tests passed” without trustworthy test-run evidence;
- a review rerun omits an old blocker and accidentally appears clean;
- a parent model skips a helper, swaps a verdict slot, or reconstructs scope differently;
- a generated graph is hand-wired after generation;
- an invariant is called “enforced” although only a reviewer remembers it;
- a retry or Git staging recipe is improvised differently on each harness.

Loom moves those decisions into types, parsers, hashes, reducers, exact rosters, protected state, and anchored persistence.

## 1. Executable models only

The standing policy is: **a model either executes or it does not exist**.

### Lifecycles

A plan may declare an `LC-N` machine file. Decompose must bind that file to a Task, and implementation imports the typed reducer/statechart rather than reimplementing its transitions.

The Wave Gate verifies the declared artifact exists. Property tests and normal compilation prove behavior; paired lint invariants can forbid duplicated state literals or forbidden imports.

### Pipelines

When a project uses Fugue and the user opts in, architecture may author an `AuthoredDag` sidecar. Graph code is generated by Fugue, not hand-written. Generated TypeScript carries an `@fugue-integrity` hash over its structural projection; Loom’s full-tier `fugue-generated-integrity` rule recomputes it while excluding sanctioned `@fugue-body` regions.

This is a separate concern from Loom’s own use of Fugue for internal orchestration programs. Internal programs call Fugue 0.4.0’s public runtime directly and do not require an `AuthoredDag` sidecar.

### Invariants

A plan’s `INV-N` is either:

- `checkable`, with a real project lint-rule file loaded fail-closed; or
- `advisory`, explicitly unenforced prose.

The architecture phase writes and validates checkable rule artifacts before implementation. A rule that cannot test the real property must not be called checkable.

Exact grammar and enforcement points are documented in [Executable Models](../references/executable-models.md).

## 2. Proof obligations, not completion claims

`core/proof-obligations.ts` derives Task completion authority from declared policy and observed evidence. Obligations may include:

- successful Agent completion;
- a passing regression test result;
- new tests written;
- every declared artifact changed.

A Task reaches `implemented` or `completed` only when its proof is `satisfied`. Missing, failed, stale, untrusted where trust is required, or incomplete evidence keeps it pending.

The proof object is engine-authored. Agent prose is input evidence, not the verdict.

## 3. Evidence ledger and guarded skill machines

`engine/src/machine/` records facts—`FileRead`, `FileWrite`, and `TestRun`—under a per-Agent epoch. Reducers derive phase and test judgments from those facts.

A report-backed test run can produce `trusted-pass` or `trusted-fail`. A transcript-only signal remains explicitly `untrusted`; Pi’s paired structured evidence remains labeled `pi-structured`. Provenance is never upgraded merely because a consumer prefers a boolean.

The code-implementer machine enforces `read-context → implement → verify → done` when one Agent can be attributed unambiguously. During parallel activity, Claude tool events do not carry enough child identity; the live gate and recorder stand down rather than cross-credit one Agent’s work to another. SubagentStop still audits whatever epoch-specific evidence exists.

Report freshness is call-scoped, duplicate tool deliveries are deduplicated by call id, and later file writes can invalidate an earlier pass. Detailed limits are in [Guarded Skill Machines](../machines/README.md).

## 4. Protected state

The active TaskGraph is orchestration authority. If an Agent could edit it, it could forge phase completion, tests, Findings, or Wave advancement.

Protection has four layers:

1. mode `0444` at rest;
2. a deny-by-default Bash guard over state, evidence/binding, and machine paths;
3. `StateManager` lock plus temporary-file/rename writes;
4. narrow hook/helper ownership of mutations.

### Shell normalization

Bash can reassemble the same path through quotes, ANSI-C strings, parameter expansion, brace/glob forms, substitutions, wrappers, and heredocs. `core/guard-state-file.ts` evaluates reveal-monotonic command views and recursively judges live substitutions and script-bearing heredoc bodies.

The guard distinguishes data from executable stdin: prose in a quoted heredoc is not treated as a command unless the heredoc feeds an interpreter/evaluator path. Common wrappers and fused spellings are normalized before judgment.

Unparseable or unbounded forms fail closed. The documented residual class is syntax a raw command-text gate cannot infer, especially multi-hop cwd laundering that never contains a guarded path literal.

## 5. Immutable review scope

A Review Packet is a canonical immutable snapshot binding one Task to:

- Review Generation;
- base/head revisions;
- exact declared and modified paths;
- diffs and byte-preserving postimages;
- plan context;
- proof obligations.

The protected graph records an engine-issued packet registration atomically with Review Run creation. Packet self-hashes prove integrity; registration proves issuance. A caller-authored file with recomputed hashes is not historical authority.

A Review Run freezes the packet, exact reviewer roster, and ordered prior Finding ids. Every expected reviewer must assess every prior id exactly once. Finalization is atomic: old Findings resolve and new Findings activate together, or neither change occurs.

## 6. Finding identity and adjudication

Review models emit draft claims. The engine assigns identity from Agent and emission order. Stable identity enables two distinct terminal treatments:

- **Resolved Finding** — implementation changed and the complete packet-bound reviewer roster verified remediation.
- **Refuted Finding** — the claim was adjudicated as not holding, with lenses/votes/reasoning retained.

A clean reviewer output cannot delete an old Finding by omission. A manual override is stored as an audited refutation-like decision rather than silent deletion.

## 7. Exact panels

Architecture and refutation panels share `core/panel-kernel.ts` but retain distinct lens vocabularies and outcomes.

Exactness is structural:

- a manifest/authority freezes every item and every slot;
- each verdict must cover the exact item set once;
- missing, duplicate, foreign, or surplus entries fail;
- slot identity binds lens or criterion, so caller prose cannot swap it;
- malformed semantic output receives one retry;
- aggregation/tally accepts only a parser-produced complete roster.

Architecture ranking is deterministic. Refutation requires a strict majority; ties preserve the critical.

## 8. Engine-owned orchestration programs

Wave Gate, standalone review, remediation, architecture panel, and refutation panel are closed reducers with explicit state/event unions. Their public boundary returns only:

- `spawn-batch`;
- `await-user`;
- `blocked`;
- `done`.

The parent does not build event arrays, retry policy, reviewer lists, model lookups, or result JSON.

### Request authority

Every request binds Run, request, slot, attempt, program, role, model profile, both harness bindings, required Skill, Context Packet digest, and output slot. Pi/Claude native ids are correlators to that authority, not substitutes for it.

### Events, checkpoints, and receipts

The Fugue-backed runtime stores immutable events and a checkpoint projection. Event append precedes checkpoint update; dedup keys make the crash window replay-safe. Effects produce typed receipts. Resume reconciles an existing receipt instead of repeating the effect.

### Narrow capabilities

Static operation DAGs receive only the capabilities they declare: run-artifact publication, protected-state commit, or Git-index operations. Validation and routing nodes receive none.

## 9. Anchored Run Directories

`RunDirHandle` requires an existing direct child of a declared runs root and exposes only fixed layout operations. It has no arbitrary-path write method.

Authority, request, context, transcript, event, receipt, and artifact publication use anchored no-follow filesystem operations. Immutable slots are exclusive. A symlink swap, traversal component, duplicate publication, or mismatched run identity fails closed.

This protects semantic evidence from both accidental path bugs and prompt-controlled output paths.

## 10. Verified remediation index

The remediation reducer accepts authority only from an adjudicated standalone result plus explicit support paths. It excludes Loom state/review/run evidence.

The Git shell:

1. observes dirty/staged paths;
2. proves all are authorized;
3. stages literal paths in a temporary index;
4. proves staged equals audited;
5. records repository witnesses;
6. rechecks under the real index lock;
7. atomically installs the verified index.

Deleted and absent paths are first-class states. A missing temporary index is never interpreted as the real index. The parent cannot replace this with `git add` and preserve the guarantee.

## 11. Fail-closed lint

Loom’s linter has two tiers:

- immediate: regex rules after edits, with static ReDoS analysis and a per-file deadline;
- full: regex plus programmatic rules at Wave Gate or explicit scan.

Malformed rule JSON, unsafe regex, timeout, and handler crash are errors, not passes. Programmatic rules enforce import boundaries, pure-module I/O restrictions, function length, and Fugue generated integrity.

## 12. Explicit models and Skills

Every Agent has one semantic LLM profile with complete Claude Code and Pi targets. Every request includes an exact required Skill (or none). Missing catalog entries, stale Pi renders, wrong Agent scope, unresolved package roots, and mismatched model/Skill declarations block spawn.

Model calibration uses deterministic matching over vulnerable/fixed historical cases. Incomplete execution cannot be called passed, and novel predictions are not mislabeled false positives.

## Before and after

| Concern | Prompt-only failure | Deterministic authority |
|---|---|---|
| Task completion | Agent says “done” | Engine-derived proof obligations |
| Tests | Transcript text looks green | Provenance-preserving ledger/structured evidence |
| Review rerun | Old blocker omitted | Generation + packet + exact prior-id assessments |
| Panel | Caller swaps or skips verdicts | Exact slots and complete-roster parser |
| Retry | Parent improvises | Typed attempt-1/attempt-2 lifecycle |
| Workflow order | Markdown sequence | Reducer state/event algebra |
| Transcript persistence | Parent copies output | Harness captures exact bytes into fixed slots |
| State writes | Agent edits JSON | Guard + StateManager + typed commit effect |
| Run artifacts | Prompt chooses paths | Anchored fixed-layout RunDirHandle |
| Git staging | Broad `git add` | Audited temporary index and witness recheck |
| Invariant | Reviewer remembers | Checkable lint rule or honest advisory prose |
| Generated pipeline | Hand-wired drift | Fugue stamp + Loom integrity verification |

## Honest limits

Determinism is scoped to what Loom can observe and own:

- semantic design/review correctness still depends on models and user judgment;
- Claude’s live per-Agent evidence attribution cannot be sound during ambiguous parallel tool activity, so it stands down;
- report artifacts remain in an Agent-writable environment, with documented same-call forgery residuals;
- the shell guard judges command text, not an abstract Bash execution graph;
- Pi cannot yet relay interactive phase questionnaires into headless child processes;
- legacy readers remain for historical evidence but are frozen in `core/legacy-archive.ts`.

These are documented boundaries, not silent claims of enforcement.
